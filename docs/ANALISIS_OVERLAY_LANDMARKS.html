3. ¿Por qué es muy necesario para modo dinámico?

✔️ Marcadores no-manuales (NMM)

En LSEC y otras LSE, las señas se distinguen por la expresión facial tanto como por la mano:

  • Cejas levantadas → pregunta (sube cejas + signo manual)
  • Cejas fruncidas → negación / afirmación enfática
  • Forma de boca (boca cerrada = adverbio, abierta = verbo)
  • Dirección de mirada → apunta al referente
  • Movimiento de cabeza → afirmación/negación sin manos

El modelo de 147 dims actual solo tiene nose (0,0,0) → ceguera total a NMM.

📍 Contacto mano-cara

Muchas señas dinámicas de LSEC se definen por dónde toca la mano la cara:

  • MAMÁ: pulgar en mejilla
  • PAPÁ: pulgar en frente
  • CASA: mejillas (boca abierta)
  • BEBER: mano en boca
  • NOMBRE: dedo medio cruza el pecho

Sin landmarks faciales, el modelo no puede medir la distancia mano→frente vs mano→mejilla.

🔄 Trayectorias en el espacio facial

Las señas dinámicas son recorridos, no poses. Necesitas puntos de referencia estables:

  • Ojos fijos (para medir desviación de cabeza)
  • Nariz fija (para medir trayectoria)
  • Orejas (para calcular rotación 3D de la cabeza)
  • Borde de la mandíbula (límite inferior del espacio de señas)

Con FaceLandmarker obtienes ~10 puntos rígidos en el cráneo + 4 en mandíbula.

⚠️ Falso negativo actual

Durante las pruebas F7 (sub-agente lsc-user-validator) las señas cerca de la cara fallan porque:

  1. La mano ocluye parte de la cara → PoseLandmarker pierde el hombro/nariz.
  2. Sin rostro detectado, normalizeHolistic() usa solo mano y la seña se vuelve ambigua.
  3. El usuario no sabe por qué falló: hoy no ve nada en pantalla.

Un overlay mostraría en vivo: "Cara no detectada, aléjate 30 cm".

4. Pipeline propuesto (integración mínima)

// ─── 1) HandDetector.kt — añadir FaceLandmarker ───
import com.google.mediapipe.tasks.vision.facelandmarker.FaceLandmarker

private var faceLandmarker: FaceLandmarker? = null

// init(): mismo `tasks-vision:0.10.9` ya en libs.versions.toml
faceLandmarker = FaceLandmarker.createFromOptions(context,
    FaceLandmarkerOptions.builder()
        .setBaseOptions(BaseOptions.builder()
            .setModelAssetPath("face_landmarker.task").build())
        .setRunningMode(RunningMode.VIDEO)
        .setNumFaces(1)
        .setOutputFaceBlendshapes(true)   // 52 expresiones → NMM
        .build())

// ─── 2) Nuevo retorno “raw” para overlay (sin romper el modelo) ───
data class LandmarkFrame(
    val leftHand:  List<List<Float>>,   // 21×3
    val rightHand: List<List<Float>>,   // 21×3
    val face:      List<List<Float>>,   // 478×3
    val blendshapes: FloatArray,         // 52 (NMM)
    val pose:      List<List<Float>>    // 33×3
)

// ─── 3) CameraScreen.kt — overlay Compose Canvas ───
Box(Modifier.fillMaxSize()) {
    AndroidView({ previewView })                // cámara debajo
    Canvas(Modifier.fillMaxSize()) {             // overlay arriba
        drawHandConnections(leftHand, color = Orange)
        drawFaceContours(face, color = Violet)
        drawPoseSkeleton(pose, color = Green)
    }
    ResultsOverlay(uiState)                     // UI inferior
}

6. Impacto en rendimiento (estimado)

Hoy (sin cara)

~12 ms/frame en Pixel 5 · 30 fps estable

  • HandLandmarker · 2 manos · ~7 ms
  • PoseLandmarker · ~5 ms
  • Dibujo Compose · < 1 ms

Propuesto (con cara)

~20 ms/frame en Pixel 5 · 30 fps aún estable

  • HandLandmarker · ~7 ms
  • PoseLandmarker · ~5 ms
  • FaceLandmarker Lite · ~6 ms
  • Canvas (478 pts + 2×21 pts) · < 2 ms

Si quieres ultra-ligero

~15 ms/frame · ahorra 5.8 MB de APK

  • Drop PoseLandmarker
  • Usar solo nariz/ojos/boca de FaceLandmarker como anclas de pose
  • Modo refineLandmarks=false

7. Veredicto final

✅ Recomendación

SÍ, es viable y muy recomendable. La librería ya está en el proyecto (tasks-vision:0.10.9); solo falta:

  1. Bajar face_landmarker.task a assets/.
  2. Refactorizar HandDetector para exponer landmarks crudos.
  3. Añadir un Canvas { } sobre el PreviewView.
  4. (Opcional) Re-entrenar el clasificador con NMM para subir accuracy en modo dinámico.

Sin cambios en Gradle. Sin nuevas dependencias. Sin riesgo de regresión mayor si conservas el FloatArray(147).
